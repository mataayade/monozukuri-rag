## 2. 観点別の比較

### PDF 取り込み（表の扱い）
- LangChain 系例・folder-rag-ja・Archit-Konde: 文字の抽出のみ（PyMuPDF / pypdf / PyPDF2）。表の専用処理は見当たらない。表は文字の並びとして崩れる可能性が高い（推測）。
- RAG-Japanese: CJKPDFReader。表の専用処理は README に記載なし。
- PyMuPDF には `Page.find_tables()`（ページ上の表を見つけて返す）がある。出典: https://pymupdf.readthedocs.io/en/latest/page.html
- ライセンス: pymupdf4llm リポジトリは AGPL-3.0 と表示。PyMuPDF 本体も同系の可能性が高いが未確認。公開リポジトリでの利用条件は段1で要確認。代替は pypdf / pdfplumber（未調査）。
- 数百ページの白書は、ページ番号つきで抽出し、表は find_tables で別扱いにして文字に直す、が最小案。図の中の文字は取れない（OCR なし）と割り切る。

### 分割
- LangChain 系: RecursiveCharacterTextSplitter（区切り文字の優先順で再帰的に分ける。文字数ベース）。
- Archit-Konde: 自前の再帰分割、512 文字 / 重なり 64。
- japanese-knowledge-rag: 見出し（第N章・第N条）で分割。
- 白書は章・節の見出しがあるので、「見出し優先 + 文字数上限 + 重なり」の自前分割が説明しやすい。各チャンクにページ番号を持たせる。粒度は段4で実測して決める。

### 埋め込みモデル
- bge-m3: Ollama で `ollama pull bge-m3`。567M パラメータ、1.2GB、文脈 8K トークン、100言語以上、取得 810 万回。出典: https://ollama.com/library/bge-m3
- 日本語検索の比較（JQaRA, nDCG@10）: BM25 0.458 / bge-m3 dense 0.539 / multilingual-e5-large 0.554 / ruri-large 0.629。出典: https://github.com/hotchpotch/JQaRA
- ruri は日本語専用で精度が高い。HuggingFace に cl-nagoya/ruri-v3-310m（Apache-2.0、0.3B、8192 トークン）があるが、Ollama 公式一覧では確認できず、別の動かし方が要る。
- 他に Ollama にあるもの: qwen3-embedding, snowflake-arctic-embed2（多言語）, granite-embedding 278m（多言語）, embeddinggemma, nomic-embed-text-v2-moe。出典: https://ollama.com/search?q=embedding 。日本語での優劣は未確認。
- 結論: 既定は bge-m3（Ollama で一発、日本語の実績あり）。余力があれば ruri との比較を「改善の前後比較」の1つにできる。

### 検索（ベクトル / BM25 / 併用、形態素解析は要るか）
- 併用の方法: folder-rag-ja は重み付き和、Archit-Konde と japanese-knowledge-rag は RRF（順位の逆数を足して統合）。JQaRA では bge-m3 が BM25 を上回るが、BM25 も大きく劣るわけではない。併用で伸びる傾向（推測）。
- 日本語 BM25 の語の切り方: (a) 形態素解析（Sudachi / MeCab / fugashi。辞書が要る）、(b) 文字 n-gram（辞書不要。folder-rag-ja は2-gram）、(c) 文字種の切れ目（japanese-knowledge-rag）。形態素解析と n-gram の精度差を示す資料は今回見つからず（未検証）。
- 結論: 形態素解析は必須ではない。文字 2-gram なら数行で書けて説明しやすい。「2-gram vs 形態素解析」自体を比較実験にもできる。

### 評価方法
- RAGAS: faithfulness（根拠への忠実さ）、context precision / recall、response relevancy などの指標。LLM を採点役に使う指標がある。出典: https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/ （どの指標が LLM 必須かはページに明記なし。日本語での採点品質は未確認）。
- 例の実践: japanese-knowledge-rag は自作問題で正答数・誤引用数・Recall@5・MRR。koheip/rag-doc-qa は Hit@k・MRR + LLM 採点。Archit-Konde も Precision/Recall/MRR。
- 結論: 計画どおり自作20問が主。検索は Hit@k / MRR（正解ページが上位に入ったか。自前で数行）、回答は「正答 / でっち上げ / 正しく『ない』と答えた」を人手で採点。RAGAS は任意の追加（説明の負担が増えるので初回は入れない）。

### 画面
- Streamlit が多数派（Archit-Konde, folder-rag-ja, koheip/rag-doc-qa）。計画どおり Streamlit。出典ページ表示と「検索された断片の展開」を付けると評価と説明に使える。

## 3. 推奨構成

| 部品 | 選択 | 自前か既製か |
|---|---|---|
| PDF 読み取り | PyMuPDF（ページ番号つき抽出 + find_tables で表）。ライセンス要確認 | 既製 |
| 分割 | 見出し優先 + 文字数上限 + 重なり。各チャンクにページ番号 | 自前 |
| 埋め込み | bge-m3（Ollama）。比較実験で ruri など | 既製 |
| 検索 | 自前 BM25（文字2-gram）+ 自前コサイン類似度（NumPy）+ RRF で統合 | 自前 |
| ローカル LLM | Ollama 上の日本語に強い中型モデル（qwen3 系など。具体名は段3で実測して決める） | 既製 |
| API LLM | Gemini と Claude を同じプロンプトで比較 | 既製 |
| 画面 | Streamlit | 既製 |
| 評価 | 自作20問 + Hit@k / MRR（自前）。RAGAS は任意 | 自前 |

理由:
1. 課題は「分割・類似度検索を自力で組めるか」を見る。そこに LangChain / LlamaIndex を使うと、説明できない箱が増える。自前なら BM25 の式、コサイン類似度、RRF が各数行〜数十行で、1〜2文で説明できる。
2. PDF 読み取り・埋め込み・LLM・画面は自作の学習価値が低く、既製品の方が精度も安全性も高い。
3. 検索を BM25 とベクトルに分けて自前で書くと、「どちらが効くか」の前後比較（完成の基準4）がそのまま作れる。
4. 近い実例（folder-rag-ja: bge-m3 + 2-gram BM25 + Streamlit + Ollama）があり、全体構成が成立する裏付けになる。コードは写さず、設計の確認にだけ使う。

初心者が説明しやすいか: 高い。外部部品は「PDFから文字を取る」「文字を数値の列にする」「文章を作る」「画面」の4つで、入力と出力だけで説明できる。自前部分は式が短く、数字を手で追える。

要確認（段1以降に持ち越し）: PyMuPDF のライセンス条件 / 白書での表の崩れ方 / bge-m3 と ruri の差 / ローカル LLM の具体モデル（GPU メモリ次第）/ 2-gram と形態素解析の差。
